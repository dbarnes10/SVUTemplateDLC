# SVUTemplateDLC

A starting point for writing a downloadable content (DLC) plugin for the Swinburne Virtual Universe (SVU) software.

A DLC plugin is some Unity content plus a small C# assembly. You build both in this project and export them as a package. The SVU host loads the package at runtime on the display, without being rebuilt itself.

DLC plugins for SVU are currently in development. The WebUI is not yet available so plugins can be loaded and displayed, but not controlled beyond SVU standard camera controls.

DLC plugins for SVU will support cluser mode (mostly) transparently to the user. Curently cluster mode is being finalised and is not yet supported.

This repository contains one working plugin, **TemplateDLC**, and the editor tools to set it up, check it and export it. All the tools live in one menu, **SVU DLC**.

---

## Requirements

- **The same Unity version as the SVU host.** The host rejects packages built with any other version. The project is set up for **Unity 6000.4.12f1**; check with the SVU team if the host has moved on.
- URP 17 and Addressables 2.x, both already included.
- The framework's interface DLL, which ships in `Assets/Plugins/DLCFramework/`. You don't need the host project, but you can use it to test your plugin if you want a lighter-weight test environment than the full SVU.

## Quick start

1. **Fork then clone the repository and open it in Unity.**
2. **Set up your plugin: SVU DLC ▸ Plugin Settings….**
   - Enter a plugin name (e.g. `Galaxy`) and your organisation's domain (e.g. `swinburne.edu.au`).
   - Fill in the display name, version, author and description, then click **Apply and Rename**.
   - Commit to git first; renaming can't be undone. See [Plugin settings](#plugin-settings).
3. **Open SVU DLC ▸ Open Content Scene** and build your content under `GalaxyContent`. See [Building your content](#building-your-content).
4. **Choose SVU DLC ▸ Check Content** to see what will ship and what won't.
5. **Choose SVU DLC ▸ Build and Export…** and click **Build and Export Package**.
6. **Copy the exported `au.edu.swinburne.galaxy/` folder** into the host's DLC folder (by default `<persistentDataPath>/DLC/`). The host loads it by its package ID.

(correction required:) Before you change anything, it's worth exporting the untouched template once and loading it on the host. You should see an **orange cube**. If you do, the whole pipeline works, including wiring. A white or blue cube means part of wiring failed (see [Troubleshooting](#troubleshooting)). In the editor the cube is blue until you press Play; the orange is applied at runtime.

## The SVU DLC menu

| Item | What it does |
|---|---|
| **Plugin Settings…** | Edits the plugin's identity: name, organisation domain, display name, version, author, description, 2D/3D. Changing the name or domain renames the plugin. |
| **Open Content Scene** | Opens the scene you build your plugin in. |
| **Check Content** | Builds the plugin's content from the scene and reports, in the Console, anything that won't ship or won't work on the wall. It's quick; use it often. |
| **Build and Export…** | Runs Check Content, then builds the full package for the host. |

## Project layout

```
Assets/
  TemplateDLC/                  ← your plugin (renamed by Plugin Settings)
    TemplateScene.unity         ← THE SCENE YOU BUILD IN
    TemplateDLC.cs              ← plugin entry point: instantiate, wiring, web UI hooks
    TemplateBehaviour.cs        ← example script (replace or delete)
    TemplateDLC.asmdef          ← plugin assembly → TemplateDLC.dll
    manifest.json               ← identity — edit through Plugin Settings
    Materials/TemplateMaterial.mat
    Build/                      ← generated by Check Content — never edit
  DLCTools/Editor/              ← the SVU DLC tools
  Plugins/DLCFramework/         ← DLCFramework.Interfaces.dll (do not modify)
  Settings/                     ← URP pipeline asset
```

Everything in the plugin folder compiles into one assembly, `TemplateDLC.dll`, which ships in the package. Put your own scripts, materials, textures, models and sub-folders anywhere inside it.

## Building your content

`TemplateScene` has two root GameObjects:

- **`TemplateContent`**: your plugin. **Everything under it ships**, and nothing else does.
- **`Preview Camera`**: for looking at your work in the editor. It never ships; on the wall, the host provides the camera.

Build under `TemplateContent` as in any Unity scene: GameObjects, meshes, materials, particle systems, prefabs and your own scripts, all set up in the Inspector. Anything else you add outside `TemplateContent` is preview-only: stand-ins, test objects, a different camera angle. Keep the root's name; it's how the tools and the plugin find your content.

The root's position in the scene is only for previewing. On the wall, the host places your content at the subwindow's spawn position.

These components can't go under `TemplateContent`, because the host owns them. Check Content reports an error if it finds one:

- Camera
- AudioListener
- post-processing Volume

### Lighting

On the wall, each plugin is lit only by its own lights: the host's lights don't reach it, and its lights don't reach the host or other plugins.

`TemplateContent` includes a **Directional Light**, so your content ships with its own lighting. Things to know:

- **Keep your lights under `TemplateContent`.** A light elsewhere in the scene lights your preview but doesn't ship, and Check Content warns you about it.
- **Keep lights set to Realtime.** Baked lighting belongs to the scene and doesn't ship.
- **Ambient light, skybox and reflections aren't part of a plugin.** The template scene has them turned off, so the editor shows only your own lights.
- **Use SVU's lighting instead:** remove the Directional Light, and your content will be lit by the SVU environment.
- **Objects your scripts create at runtime.** Renderers or lights created in `Awake` or `OnEnable` are handled automatically. If you create them later, for example in `Start` or on demand, stamp them yourself:

  ```csharp
  DLCFramework.DLCLightingScope.Apply(newObject, context.LightingLayer);
  ```

### Your scripts

**Write ordinary MonoBehaviours.** There's no base class and no interface to implement.

**Keep every script inside the plugin folder**, so it compiles into the plugin assembly. A script elsewhere, for example loose in `Assets/`, ends up in an assembly the host doesn't have, and Check Content refuses it.

**Why the build strips your scripts.** The host loads your DLL at runtime, after Unity has deserialised the content, so Unity can't bind your scripts from the bundle. The build therefore strips them and records their Inspector values and references. When your plugin instantiates its content, the host adds the scripts back and restores their fields *before* `Awake` runs. From your script's point of view it behaves like normal Unity.

**What is restored automatically:**

| Kind | Types |
|---|---|
| Values | `float`, `int`, `bool`, `string`, enums, `LayerMask`, `Vector2/3/4`, `Color`, `Color32`, `Rect`, `Bounds`, `Quaternion`, `AnimationCurve` |
| References inside your content | any Component or GameObject under the content root |
| References to assets | materials, textures, meshes, audio, ScriptableObjects, prefabs. The build makes them addressable for you. |

**What is not restored.** Check Content warns about each of these; set them up in code instead, for example in `Awake`:

- arrays and `List<>`s
- nested `[Serializable]` classes or structs
- `UnityEvent`s
- `[SerializeReference]` fields
- `double`, `long` and other types not in the table above
- references to Unity's built-in resources, such as the default cube mesh
- references to objects outside the content root

This only applies to fields on *your* scripts. Unity's own components (MeshRenderer, Light, ParticleSystem …) ship as they are.

**The `DLCIdentity` component.** Check Content adds a small `DLCIdentity` component to some GameObjects. Its ID is how the host matches your scripts back to their GameObjects, so leave it alone. Duplicating GameObjects is fine; duplicate IDs are repaired automatically.

### Running on a cluster

The wall is driven by several PCs, and every one of them runs your plugin. Anything that depends on per-machine timing or randomness will drift apart across the screens.

Drive shared state through settables (see [Web UI](#web-ui-settables)). The master node owns their values and syncs them to every node.

## The plugin class

`TemplateDLC.cs` is the entry point. The host finds it by reflection, so it must be the **only public class implementing `IDLCPlugin`** in the assembly. It has three hooks, marked `[1]`, `[2]` and `[3]` in the code:

1. **Instantiate.** `context.InstantiatePrefab(ContentAddress, context.SpawnPosition)` loads your content from the bundle. Keep it.
2. **Wiring.** Already complete when `InstantiatePrefab` returns: your scripts are present, their fields are set, and `Awake`/`OnEnable` have run. To reach one, use `GetComponentInChildren<T>()` on the returned root.
3. **Web UI.** A commented-out example slider; search for `[WEB-UI]`.

The class's `Id` and `Version` must match `manifest.json`. Plugin Settings keeps them in step, so change them there rather than in code.

### Web UI settables

Each plugin gets a tab in the SVU web interface. Uncomment the `_params["scale"] = …` line in `OnLoaded` to add a Scale slider. `ApplyParams()` already applies it.

To add your own parameter:

1. Add an `svuSettable` to `_params` in `OnLoaded`. There are constructors for floats, ints, bools, strings, choices (dropdowns), colours, vectors, ranges and gradients. Group them with `.InGroup("…")`.
2. Apply it in `ApplyParams()`.

`ApplyParams()` runs in three places:

- on load
- on the master node when a value changes (`svuSetterCallback`)
- on every other node after a cluster sync (`OnStateReceived`)

Because every node goes through the same code path, the wall stays consistent.

## Plugin settings

**SVU DLC ▸ Plugin Settings…** is the one place to edit the plugin's identity. It writes `manifest.json`, the file the host reads, and updates the plugin class's `Id` and `Version` to match.

The **package ID** is derived from your organisation domain and plugin name: `swinburne.edu.au` + `Galaxy` → `au.edu.swinburne.galaxy`. It must be unique on the host, so replace the template's `example.com` before sharing a plugin.

**Changing the name or domain renames the plugin.** Every occurrence of the old names inside the plugin folder is replaced, file names included:

| Before | After (`Galaxy`) |
|---|---|
| `Assets/TemplateDLC/`, class, assembly | `Assets/GalaxyDLC/`, `GalaxyDLC` |
| `TemplateScene.unity` | `GalaxyScene.unity` |
| `TemplateContent` (content root, bundle address) | `GalaxyContent` |
| `TemplateBehaviour`, `TemplateMaterial` | `GalaxyBehaviour`, `GalaxyMaterial` |
| `com.example.template` | `au.edu.swinburne.galaxy` |

Files move together with their `.meta` files, so GUIDs and every reference survive. Build output carrying the old names is deleted; run Check Content afterwards.

You can rename at any time, not just the first time, but **commit to git first**: a rename can't be undone.

## Building and exporting

**Build and Export…** runs Check Content, then the Addressables build, and assembles the package. By default it goes in `DLCOutput/`, next to this project folder; you can change that in the window. The window also checks that `manifest.json` and the plugin class agree before it lets you export.

```
DLCOutput/com.example.template/
  manifest.json                  (stamped with your Unity version)
  code/TemplateDLC.dll
  addressables/StandaloneOSX/    (or StandaloneWindows64 — the active build target)
```

Export once per platform the wall runs on. Switch the build target in **File ▸ Build Profiles** first.

## Troubleshooting

**The cube isn't orange on the wall.** `TemplateBehaviour` tints it in `Start` using two wired fields, so the colour tells you what failed:

| Colour | Meaning |
|---|---|
| Orange | Wiring works. |
| White | The script and its `targetRenderer` reference were restored, but its `tint` value wasn't (white is the code default). |
| Blue | The script wasn't re-added, or `targetRenderer` wasn't restored. You're seeing the material's own colour. |

Check the host Console for `[DLCWire]` messages. The host needs a UnityDLC version with prefab wiring; older hosts load the content but skip wiring.

**Your content is dark on the wall.** Its light is outside the content root, so it didn't ship. Check Content warns about this.

**The host reports "Unity version mismatch".** Rebuild with the host's exact Unity version.

**The host reports "Type '…' not found in assembly".** A script was renamed or removed after the content was built. Build and export again.

**Check Content reports a script "from assembly Assembly-CSharp".** That script is outside the plugin folder. Move it in.

**Check Content warns that a field "is not restored by wiring".** See [Your scripts](#your-scripts); set that field up in code.

**The host reports "Content 'TemplateContent' not found in the bundle".** The package is stale or was built under a different name. Export again.
